# Phase 5: Chat Management & Persistence — Specification

**Created:** 2026-09-09  
**Ambiguity score:** 0.04 (gate: ≤ 0.20)  
**Requirements:** 4 locked  

## Goal

Реализовать полный жизненный цикл управления диалогами и сохранения переписки в MongoDB с контекстной памятью: предоставить REST API для CRUD операций над чатами, сохранять реплики пользователя и ассистента с метриками токенов/стоимости, собирать скользящее окно истории для отправки в routerai.ru и обеспечить каскадную очистку при удалении чата со строгой мультитенантной изоляцией пользователей.

## Background

В фазах 1–4 реализована основа платформы: аутентификация через VK OAuth, учет баланса в PostgreSQL, клиент routerai.ru со стримингом SSE и биллингом токенов. При этом в Phase 2 уже были заложены структуры `Chat` и `Message` и базовые репозитории MongoDB (`ChatRepository`, `MessageRepository`), но они не были связаны с HTTP-сервером и стримингом. Пользователи могли генерировать текст через `POST /api/v1/chat/stream` только в stateless-режиме: без сохранения сообщений, без списка предыдущих диалогов и без памяти контекста между репликами.

Phase 5 переводит систему в stateful-режим: чаты сохраняются, пользователь видит свою историю, а LLM получает предшествующий контекст диалога.

## Requirements

1. **Chat Session CRUD & Tenant Isolation (R1 - CHAT-01)**: Реализован HTTP REST API для управления диалогами в MongoDB с изоляцией на уровне пользователей.
   - Current: В MongoDB определена схема `chats` и методы `ChatRepository`, но HTTP эндпоинты отсутствуют, а репозитории не подключены к `server.Router`.
   - Target: Сервисный слой и REST-эндпоинты предоставляют полный цикл управления чатами:
     - `POST /api/v1/chats` — создание диалога (название опционально, по умолчанию «Новый диалог», модель опционально или дефолтная системная).
     - `GET /api/v1/chats` — список диалогов аутентифицированного пользователя с пагинацией (`limit`, `offset`), отсортированный по `updated_at DESC`.
     - `GET /api/v1/chats/{id}` — получение информации о диалоге по его ObjectID.
     - `PATCH /api/v1/chats/{id}` — обновление названия (`title`) диалога.
     - `DELETE /api/v1/chats/{id}` — удаление диалога с каскадным удалением всех его сообщений.
     - Доступ ко всем эндпоинтам защищен JWT-авторизацией. Попытка чтения, модификации или удаления чужого диалога возвращает HTTP 404 Not Found (не раскрывая факт существования ресурса).
   - Acceptance: Интеграционные тесты подтверждают корректную работу всех CRUD-операций и гарантируют, что пользователь А не может получить доступ к чатам пользователя Б, получая HTTP 404.

2. **Message Persistence & Auto-titling (R2 - CHAT-02)**: Сохранение сообщений диалога в MongoDB с метаданными токенов и автоматическое именование первого диалога.
   - Current: Стриминг `POST /api/v1/chat/stream` не взаимодействует с MongoDB и не сохраняет историю.
   - Target:
     - При отправке запроса в `POST /api/v1/chat/stream` с указанием `chat_id`:
       1. Проверяется существование чата и его принадлежность текущему `user_id` (при отсутствии — HTTP 404).
       2. Реплика пользователя сохраняется в коллекции `messages` до начала стриминга с полями: `chat_id`, `user_id`, `role = "user"`, `content`, `created_at`.
       3. Если название чата равно дефолтному («Новый диалог») и это первое сообщение, заголовок чата автоматически обновляется первыми 40-50 символами текста пользователя с добавлением многоточия при обрезке.
       4. По завершении генерации (`StreamEventDone`) ответ ассистента сохраняется в коллекции `messages` с полями: `role = "assistant"`, `content`, `prompt_tokens`, `completion_tokens`, `total_tokens`, `cost_kopecks`, `created_at`.
       5. При обрыве соединения клиентом или ошибке LLM частичный ответ (если были получены чанки текста) сохраняется в `messages` с фактически рассчитанными и списанными токенами/копейками.
       6. Поле `updated_at` в документе чата обновляется временем последнего сообщения.
     - Предоставлен эндпоинт `GET /api/v1/chats/{id}/messages` с пагинацией (`limit`, `offset`), возвращающий историю сообщений в хронологическом порядке (`created_at ASC`).
   - Acceptance: Запрос на стриминг с `chat_id` создает записи пользователя и ассистента в `messages` с корректными токенами и затратами; при обрыве стрима сохраняется частичный ответ; `GET /api/v1/chats/{id}/messages` возвращает сохраненную последовательность сообщений.

3. **Context Assembly & Sliding Window for LLM (R3 - CHAT-03)**: Формирование контекста предыдущих сообщений диалога для передачи в LLM.
   - Current: LLM получает только тот массив сообщений, который явно прислан клиентом в запросе.
   - Target:
     - При наличии `chat_id` в запросе `POST /api/v1/chat/stream`:
       - Бэкенд загружает из MongoDB историю последних $N$ сообщений (скользящее окно, по умолчанию 20 сообщений) для данного диалога в хронологическом порядке.
       - Новое сообщение пользователя добавляется в конец истории.
       - Итоговый массив сообщений передается в `llm.Provider.StreamChat`.
       - Обеспечивается обратная совместимость: если `chat_id` не передан, обработчик работает в stateless-режиме Phase 4 (принимает готовый массив `messages` из тела запроса без персистентности в MongoDB).
   - Acceptance: При последовательных запросах в один `chat_id` в вызов LLM передаются предшествующие сообщения диалога (верифицируется тестом с `MockLLMProvider`, проверяющим историю сообщений в запросе).

4. **Cascade Message Cleanup on Chat Deletion (R4 - CHAT-01/CHAT-02)**: Каскадное удаление сообщений при удалении сессии диалога.
   - Current: `ChatRepository.Delete` удаляет только документ из коллекции `chats`, оставляя сообщения в `messages` осиротевшими.
   - Target: Метод сервиса удаления диалога удаляет документ чата из `chats` и атомарно выполняет каскадное удаление всех сообщений с данным `chat_id` из коллекции `messages` (`DeleteMany`).
   - Acceptance: После вызова `DELETE /api/v1/chats/{id}` в коллекциях `chats` и `messages` не остается ни одного документа с данным `_id` / `chat_id`.

## Boundaries

**In scope:**
- Сервисный слой `ChatService` для диалогов и сообщений.
- REST API для диалогов:
  - `POST /api/v1/chats` (создание)
  - `GET /api/v1/chats` (список с пагинацией)
  - `GET /api/v1/chats/{id}` (детали диалога)
  - `PATCH /api/v1/chats/{id}` (переименование)
  - `DELETE /api/v1/chats/{id}` (каскадное удаление)
  - `GET /api/v1/chats/{id}/messages` (история сообщений с пагинацией)
- Расширение `POST /api/v1/chat/stream`:
  - Поддержка `chat_id` (гибридный контракт).
  - Сборка скользящего окна контекста (последние 20 сообщений).
  - Сохранение сообщений пользователя и ассистента в MongoDB.
  - Авто-генерация заголовка диалога по первому сообщению (40-50 символов).
  - Сохранение частичного ответа при обрыве соединения клиентом.
- Подключение репозиториев MongoDB в `backend/main.go`.
- Unit и Integration тесты (CRUD, скользящее окно контекста, изоляция пользователей, обрыв стрима, каскадное удаление).

**Out of scope:**
- Веб-интерфейс Next.js (сайдбар диалогов, селекторы, чат-окно) — предмет Phase 6 (Next.js Frontend Interface).
- Полнотекстовый поиск по сообщениям в MongoDB (full-text search).
- Экспорт переписки в PDF или Markdown (запланировано в v2, FEAT-03).
- Ветвление диалогов (message branching / edit prior message).

## Constraints

- **Tenant Isolation**: Все операции с коллекциями `chats` и `messages` должны строго фильтроваться по `user_id` авторизованного пользователя. При попытке доступа к чужому ресурсу сервер обязан возвращать HTTP 404 Not Found.
- **Index Optimization**: Запросы на выборку чатов используют составной индекс `(user_id, updated_at DESC)`, а выборка сообщений — индекс `(chat_id, created_at ASC)`.
- **Disconnect Resilience**: При прерывании клиентского SSE-соединения частичный сгенерированный текст ассистента сохраняется в MongoDB в фоновом detached context вместе с фактически начисленными токенами и расходами.
- **Backward Compatibility**: Эндпоинт `POST /api/v1/chat/stream` сохраняет работоспособность без `chat_id` (stateless режим для прямых запросов).

## Acceptance Criteria

- [ ] Запросы `GET/POST/PATCH/DELETE /api/v1/chats` без валидного JWT возвращают HTTP 401 Unauthorized.
- [ ] Пользователь может создать новый чат (`POST /api/v1/chats`) с дефолтным названием «Новый диалог» или заданным вручную.
- [ ] Пользователь может получить список своих чатов (`GET /api/v1/chats`), отсортированный по времени последнего обновления (`updated_at DESC`).
- [ ] Пользователь может переименовать свой чат (`PATCH /api/v1/chats/{id}`) и получить обновленные данные.
- [ ] Пользователь не может просмотреть, переименовать или удалить чат другого пользователя — бэкенд возвращает HTTP 404 Not Found.
- [ ] При отправке сообщения в `POST /api/v1/chat/stream` с `chat_id` бэкенд сохраняет сообщение пользователя в MongoDB до вызова LLM.
- [ ] При первом сообщении в чате с дефолтным названием заголовок автоматически обновляется первыми 40-50 символами текста.
- [ ] При наличии истории в чате бэкенд извлекает последние 20 сообщений и передает их в LLM как контекст.
- [ ] Ответ ассистента после завершения стриминга сохраняется в MongoDB с точным указанием `prompt_tokens`, `completion_tokens`, `total_tokens` и `cost_kopecks`.
- [ ] При преждевременном обрыве соединения клиентом частичный ответ ассистента сохраняется в MongoDB с фактически израсходованными токенами.
- [ ] При удалении диалога (`DELETE /api/v1/chats/{id}`) удаляется сам диалог и каскадно удаляются все связанные сообщения из коллекции `messages`.
